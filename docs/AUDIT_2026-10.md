### Securite avant lancement

- La page `/paiement/checkout/[reference]` transmettait la configuration complete
	de la passerelle a un composant client. `toCheckoutPaymentSettings` applique
	maintenant une liste blanche pour les commandes et groupes. Test avec valeurs
	sentinelles : aucune cle privee dans les proprietes publiques. Si de vraies cles
	ont deja ete utilisees sur cette page, les renouveler chez le fournisseur et
	examiner l'exposition historique ; ce lot ne realise aucune rotation.
- Le profil ne recherche plus une derniere adresse sur le seul email d'une
	commande : le filtre utilise `clientId`. Le mot de passe exige 12 caracteres
	et respecte la limite bcrypt de 72 octets. La session navigateur courante est
	effacee apres changement ; les anciens JWT web sont maintenant refuses via
	la version de session en base. Les connexions OTP Xeuy et Keycloak ont un
	cycle distinct : ne pas annoncer une deconnexion globale de tous les canaux.
- Le bypass CSRF par cookie est retire : en production, les mutations navigateur
	exigent une origine HTTPS identique au Host public (Origin prioritaire sur
	Referer). Les sous-domaines voisins sont refuses, meme avec un cookie httpOnly.
	Sans origine/referent, le double jeton reste obligatoire pour une session cookie.
	Le Bearer seul reste compatible avec les clients natifs ; ajouter un Bearer
	a une session cookie ne contourne pas le controle. Les cookies administrateur
	et NextAuth, y compris decoupes, sont reconnus comme des sessions ambiantes.
- Les uploads et les routes d'authentification navigateur ne sont plus exemptes
	en bloc. Les appels auth sans cookie ni en-tetes navigateur restent possibles
	pour les clients natifs. Les callbacks NextAuth gardent leur protection propre ;
	les callbacks de paiement, appels internes et liens de revue manuelle gardent
	leur verification serveur. Ces exceptions CSRF ne remplacent jamais leur
	authentification. Les reponses de generation du jeton sont marquees no-store.
- Nginx doit conserver le Host public et terminer HTTPS ; la configuration
	presente utilise deja `proxy_set_header Host $host`. Le controle ne fait pas
	confiance a un X-Forwarded-Host fourni par le client. Un client HTTP utilisant
	seulement un cookie doit recuperer `/api/csrf`, conserver ce cookie et renvoyer
	le jeton dans X-CSRF-Token. Aucun domaine voisin n'est ajoute a une allowlist.
- Restent bloquants pour une qualification securite : verification du telephone,
	recette integree des sessions et du paiement. Le bypass CSRF de developpement
	reste inchange ; la protection est testee explicitement en mode production.
	La recette complete derriere Nginx reste a effectuer avant deploiement.

### Revocation des sessions web

- `User.sessionVersion` est additive : absence du champ ou du claim historique
	signifie version 0. Une modification du mot de passe depuis le profil ecrit
	le hash et incremente la version dans une seule operation conditionnelle.
	La condition porte sur le hash lu et la version authentifiee : un conflit
	renvoie 409 sans annoncer de succes. Aucun backfill de production realise.
- La reinitialisation par lien consomme le jeton encore valide et incremente
	la version atomiquement. Profil et reset invalident aussi les anciens codes
	MFA et liens de reset. Les codes MFA sont consommes une seule fois, avant
	l'emission du JWT, sous condition de version et de date de validite.
- Les validateurs JWT partages et les pages protegees relisent l'etat du compte.
	NextAuth conserve la version initiale dans son JWT et la controle dans son
	callback. Les reemissions vendeur ne recuperent pas une version plus recente
	que celle de la session appelante. Pas de cache positif de revocation.
- Le middleware passe au runtime Node.js (Next.js 15.5+), car il consulte MongoDB.
	Une panne ne donne aucun acces ; middleware, profil, compte et fiche utilisateur
	renvoient 503. Certains appelants legacy peuvent encore presenter ce refus
	comme une erreur d'authentification : ne pas confondre cela avec une revocation.
- Socket.io verifie signature, expiration et etat du compte a la connexion,
	avant les evenements entrants et toutes les 30 s. Une verification bloquee
	est interrompue logiquement apres 5 s, avec deconnexion. Les sockets web du
	processus courant sont fermes au changement du mot de passe ; une autre instance
	les ferme au prochain controle, pas instantanement. Les rooms personnelles
	existantes restent inchangees ; `web-session-<id>` distingue les sessions web.
- Les tokens OTP `domain: xeuy` gardent leur cycle independant. Un refresh token
	Xeuy n'est pas accepte comme access token par les nouveaux controles partages.
	Keycloak reste sous le controle du fournisseur ; le profil ne modifie pas son
	mot de passe localement. Aucune modification du module d'authentification Xeuy.
- Le seul principal technique sans compte conserve ici est `cron-auto-import`,
	role ADMIN, avec le marqueur signe `tokenUse: service` ajoute par le script
	d'import. Un ancien token technique sans marqueur doit etre regenere. Les JWT
	humains fictifs sans compte User ne sont plus acceptes ; utiliser de vrais
	comptes de test ou les tokens statiques de developpement deja prevus.
- Deployer les validateurs et les emetteurs ensemble, puis redemarrer toutes
	les instances Next.js/Socket.io. Une ancienne instance qui ignore la version
	ne fournit pas cette garantie. Aucun deploiement ni changement de secret fait.

Quatre tests de session cibles passent : JWT reellement signes, vrais handlers
profil/reset/MFA avec persistance simulee, reemission vendeur, jeton technique,
pannes et conflits. Des sockets locaux reels verifient le refus des evenements,
la fermeture inactive et les delais. Ces tests ne prouvent pas encore les
ecritures Mongo en concurrence reelle, le callback NextAuth de bout en bout,

### DDM+

- `staleAgentJobFilter` partage le critere de battement perime entre la reprise
	et le panneau de sante sourcing ; les anciens battements absents ou nuls
	utilisent `updatedAt`. Un echec de renouvellement arrete les battements avant
	l'annulation cooperative, afin de ne pas maintenir artificiellement le job actif.
- `enqueueAgentJob('sourcing_request', ...)` enregistre le taux minimum pour une
	piece importee dans `payload.sourcingPricing`, depuis une lecture stricte des
	reglages du serveur. Le payload appelant ne peut pas remplacer ce taux.
	Le graphe utilise ce taux et les reprises le conservent. Un ancien job sans
	snapshot reste soumis a validation humaine ; un snapshot invalide echoue.
- Limite : ce snapshot ne centralise PAS les autres parametres (change, assurance,
	transport, remises). Les autres runners n'offrent toujours pas tous une
	annulation cooperative ni une protection complete contre les anciennes tentatives.
- Correction economique apres confirmation des couts transporteur : normal
	10-15 jours = 8 000 FCFA/kg, express 3-5 jours = 11 000 FCFA/kg, maritime =
	180 000 FCFA/m3. Les anciens minimums internes non confirmes sont retires
	(defaut 0, configurable). Les prix clients restent inchanges : 8 500/kg,
	12 000/kg et 180 000/m3 respectivement.
- Le cas article a 10 000 FCFA, 1 kg, une piece, aerien normal donne maintenant
	20 250 FCFA factures et 18 250 FCFA de cout simule, soit +2 000 FCFA. Le
	-5 000 precedent venait notamment de l'ancien minimum transporteur de
	15 000 FCFA. Ce resultat n'est ni une marge de production mesuree ni une
	garantie de rentabilite de tous les paniers ; les pertes reelles restent affichees.
- `/admin/prices` separe les couts transporteur des prix factures au client.
	Tarifs internes et minimums sont modifiables par ADMIN/SUPER_ADMIN, valides
	cote serveur et desormais enregistres dans `AppConfig.shippingCosts` sur MongoDB.
	Chaque ecriture incremente une version avec controle optimiste : un formulaire
	perime recoit 409, conserve la saisie et propose un rechargement explicite.
	Les lectures interrogent le primaire MongoDB, sans cache ni repli sur un fichier
	local. Une configuration absente/corrompue ou une panne Mongo bloque le calcul.
	L'ancien fichier `data/shipping-costs.json` sert uniquement de source de migration ;
	le modifier apres migration ne modifie plus les couts utilises par les routes.
- L'API de simulation et les nouveaux enregistrements comptables transmettent
	les couts sauvegardes au simulateur. Une surcharge du prix transport client
	ne modifie plus le cout transporteur. Aucune ecriture comptable existante
	n'est recalculee. La version appliquee est renvoyee par la simulation et tracee
	dans les metadonnees des nouvelles ventes comptables.
- Perimetre : les couts transporteur internes sont communs aux instances utilisant
	la meme base MongoDB. Le worker sourcing calcule actuellement un transport
	FACTURE au client a partir de `BASE_SHIPPING_RATES`, pas un cout transporteur
	interne. Ce calcul reste inchange. Change, assurance, prix clients, frais,
	eligibilite maritime, tolerance et remises ne sont pas centralises par ce lot.
	La sauvegarde groupee de ces reglages locaux et des couts Mongo n'est pas une
	transaction multi-stockage ; apres erreur, recharger pour verifier l'etat effectif.

## 2. Le besoin, domaine par domaine

**DDM+ (marketplace).** Rendre l'achat en Chine accessible et sûr au Sénégal, là où AliExpress met trois semaines ou plus, où Temu et Shein sont absents et où des intermédiaires sur TikTok, parfois malhonnêtes, captent la demande. DDM+ achète directement chez les fournisseurs, souvent moins cher qu'AliExpress, et veut faire de chacun un entrepreneur : acheter en groupe, revendre en stock local avec sa marge, ou simplement apporter des clients. Les briques clés sont l'achat groupé payé au prix final, les boutiques en stock à Dakar, les précommandes des revendeurs, les ambassadeurs, le transport en trois modes facturé au poids réel, la garantie de paiement et le retrait en point relais.

**Xeuy Bi (services à la demande).** Un « Uber des artisans » : le client décrit son besoin (texte, photos, voix), les prestataires proches proposent un prix, la mission est suivie en direct jusqu'au paiement libéré du séquestre. L'IA aide à décrire la demande, à chiffrer l'offre et à guider la mission ; l'application parle français, anglais et wolof. Les enjeux sont la confiance (KYC, avis, litiges), la rapidité de mise en relation et le revenu des prestataires.

**Corporate (IT Vision B2B).** Le cœur historique : contrats de maintenance, interventions de techniciens, devis et factures conformes (BRS, TVA), projets avec PV de réception, et un portail entreprise multi-utilisateurs où chaque collaborateur a des droits précis. Des agents IA préparent devis et renouvellements, toujours validés par un humain.

**Socle commun.** Authentification unique, paiements (PayDunya, Wave, Orange Money, Free Money), notifications (web push, SMS, email, bientôt WhatsApp), back-office unique.

## 3. Points d'amélioration

### Sécurité
- Le rate limiter existe (`src/lib/rate-limiter.ts`, `src/lib/rate-limit.ts`) mais n'est pas appliqué sur `client-enterprise`, `quotes`, `tickets` ni sur les exports.
- Validation Zod partielle : plusieurs POST acceptent le body brut.
- `POST /api/interventions` ne vérifie pas que le `clientId` fourni est cohérent avec l'appelant.
- Les uploads sont stockés dans `public/uploads`, sans antivirus, avec des vidéos jusqu'à 100 Mo. À migrer vers un stockage objet (S3/MinIO) avec scan.
- Les refresh tokens réutilisés ne sont pas révoqués immédiatement (famille de tokens) — à vérifier dans `src/modules/xeuy/auth/session.ts`.
- `requireInterventionAccess` n'inclut pas `SUPER_ADMIN` : à harmoniser avec le reste des gardes.

### Logique métier
- Wallet et escrow sans transaction Mongo : un paiement peut être débité sans que l'offre soit acceptée en cas d'erreur intermédiaire.
- Commandes marketplace : pas de machine à états côté serveur. Reprendre le modèle de `mission-lifecycle.ts` pour les commandes, interventions, tickets et devis.
- Précommandes sans réservation de stock atomique.
- Suppression d'un client sans cascade ni soft delete (interventions, tickets, contrats et devis orphelins).
- Taux de change yuan vers FCFA possiblement figé : à confirmer, sinon la marge s'érode sans alerte.
- Les autres chemins de confirmation de paiement (vérification manuelle, polling) doivent suivre la même transition atomique que le webhook.

### Dette de code
- Modèles en doublon : `Quote` / `AdminQuote`, `Ticket` / `SupportTicket`, cinq modèles de chat.
- Quatre générateurs de devis et factures : `InvoiceGenerator.tsx` (2035 lignes), `admin/AdminQuoteGenerator.tsx` (1805), `IntelligentQuoteGenerator.tsx` (1723), page `generateur-devis`.
- Composants géants : `AdminProductManager.tsx` (3966 lignes), `ProjectManagementSystem.tsx` (2780), `EnhancedMaintenanceForm.tsx` (1669), `DynamicSchedulingSystem.tsx` (1558).

### Exploitation
- Next.js et socket.io partagent un seul processus : la montée en charge horizontale nécessite l'adapter Redis de socket.io (`ioredis` est déjà présent).
- Le scraping Playwright stealth fait partie des dépendances de l'application web : il doit vivre uniquement dans `worker/` avec sa propre image et ses propres limites de ressources.
- Couverture de tests faible au regard de la surface API. Mettre en place une CI : `type-check`, `lint`, `test:boundaries`, E2E sur les parcours critiques.
- Logs à structurer en JSON avec un champ `domain` et un `correlationId`, envoyés vers la chaîne Kafka, Logstash, Elasticsearch. Dynatrace reste l'outil APM.
- Hygiène du dépôt : `tmp_*.sh`, `tsc-errors.txt`, `tmp-build/`, `backups/`, `data/browser-profile*`, fichier `.ppsx` et une dizaine de plans éparpillés à la racine.

### DDM+ : transport au poids réel

Constat : le transport des commandes est calculé sur le poids catalogue (estimation), alors que le poids réel n'est connu qu'à la réception à Guangzhou. Pour les achats groupés, le transport par pièce était estimé à la création (`shippingCostPerUnit`) mais jamais facturé : les participants ne payaient que le produit.

Règle retenue :
- commande : le transport estimé est payé au checkout. À la pesée, écart dans la tolérance (`SHIPPING_ADJUST_TOLERANCE`, 10 % par défaut) : rien ne change. Au-delà, seul le dépassement est facturé (lien `TR-…`, à régler avant la livraison) ou remboursé (écran Remboursements). Exemple : 5,5 kg estimés, 7 kg réels en avion à 8 500 F/kg : 46 750 F payés, 59 500 F réels, 51 425 F couverts par la tolérance, complément de 8 075 F ;
- achat groupé : le produit est payé à la clôture (prix final), le transport du lot est facturé après pesée, au poids réel, réparti au prorata des pièces entre les participants payés (lien `TR-…` chacun). L'estimation par pièce est affichée dès l'inscription et intégrée au calculateur de marge revendeur ;
- règles de calcul identiques au panier (`src/lib/shipping/freight.ts`) : avion = max(poids réel, volumétrique L×l×h/5000) × tarif/kg ; bateau groupé = max(volume, poids/1000) × 180 000 F/m³ (règle de trois : 10 kg = 0,01 m³ = 1 800 F).

Mise en œuvre : saisie admin « Pesée réelle à Guangzhou » (simulation puis validation) dans la fiche commande et dans la fiche achat groupé (`POST /api/admin/market/freight`) ; références `TR-…` payables par lien comme les achats groupés (résolution, initialisation, statut, confirmation idempotente dans `confirmTransportPayment`) ; affichage côté client sur la fiche commande et dans « Ma participation » ; mention au checkout ; comparatif des 3 modes avec tarif et exemple pour 10 kg sur la fiche produit et la page groupe.

Avis « colis disponible au point de retrait » : bouton admin (commande ou groupe), message WhatsApp officiel si `WHATSAPP_TEMPLATE_PICKUP_READY` est configuré, sinon SMS (`src/lib/customer-message.ts`, repli SMS si WhatsApp échoue). Même logique pour l'avis de transport (`WHATSAPP_TEMPLATE_TRANSPORT_DUE` : corps {{1}} commande ou produit, {{2}} poids, {{3}} montant ; bouton URL `…/paiement/checkout/{{1}}` avec la référence).

Précommandes : encart « Faites des affaires avec ce groupe » visible sur chaque groupe ouvert ; coût de revient du revendeur = prix produit + transport (estimé, puis réel après pesée).

Tolérance réglable dans l'admin (Tarifs transport, bloc « Ajustement au poids réel ») : enregistrée dans `data/shipping-adjust.json`, prioritaire sur `SHIPPING_ADJUST_TOLERANCE`, 10 % par défaut, s'applique aux pesées suivantes.

Contrôle avec le dépôt de référence (`VIT/vit`, `scripts/validate-domains.ts` et `check-domain-boundaries.ts` relus, non exécutés faute de Node) :
- modèles `AmbassadorCommission`, `PickupPoint`, `ResellerPreorder` et `ArchivedDocument` (oublié jusqu'ici) classés dans `MODEL_DOMAINS` ;
- nouvelles routes couvertes par les préfixes existants, page `/precommande` déclarée ; aucun import de modèle hors domaine dans les routes market ajoutées ;
- protection CSRF : en production, toute écriture sur `/api` sans cookie de session exige l'en-tête `X-CSRF-Token`. Les écrans boutique ne l'envoyaient pas (checkout invité, inscription à un groupe, alertes, paiement, précommandes) : risque de refus 403 pour les visiteurs non connectés. Le composant `CsrfFetch` (layout market) ajoute désormais le jeton à ces requêtes et le renouvelle une fois en cas de refus. À vérifier en production avec un navigateur privé.
